# D. 判斷力 Rubric（弱模型可執行版）

每條含判準＋正例＋反例。卡住時整份掃一遍，對上哪條就照做。

## 1. 何時該升級模型（配合 dispatch.md §4）

升級的**次數門檻**在 dispatch.md §4（haiku 一次、sonnet 兩次…），本節是**訊號判準**；兩份要合併使用——任一先觸發就升級。

**判準**：出現以下任一訊號就升級，不要再重試——
- 錯誤訊息每輪都不一樣（代表你在亂槍打鳥）。
- 修 A 壞 B、修 B 壞 A（代表缺全局理解）。
- 需要同時考慮 3 個以上互相牽制的約束（如：向後相容＋離線同步＋權限）。

✅ 正例：haiku 派去批次改 import 路徑，改壞一個檔的循環引用 → 直接升 sonnet 重派整批。
❌ 反例：sonnet 修測試失敗，第三次「再試一個小改動看看」——這已違規，第二次失敗就該帶軌跡升 opus。

## 2. 何時算真的完成

**判準**：三項全滿足才算完成——
1. 驗收條件逐項有證據（測試輸出／read-back／實跑截圖）。
2. 沒有「順手發現但沒處理」的問題未記錄——指改檔過程看到的 lint error、型別 error、標了 TODO 的已知 bug、明顯的安全疑慮；要嘛本輪修掉、要嘛在回報的「附帶發現」列出。純風格偏好（命名品味、排版）不算，不必列。
3. 使用者原話的每個子句都對應到一個產出（把需求逐句列出來打勾）。

✅ 正例：「修好簽名失效誤判」→ 改了 diff 邏輯＋跑過 JsonDiffServiceTests 10 綠＋端點測試 34 綠＋回報中列出未做瀏覽器實測。
❌ 反例：「改完了，應該可以」——沒跑測試、沒 read-back，這叫「已改、未驗證」，必須如實標註。

## 3. 何時該停下來問使用者

**判準**：滿足任一就停——
- 動作不可逆且超出原需求範圍（刪資料、改 schema、push、對外發布）。
- 兩個合理方案會導致**使用者可見的行為差異**，且需求原文無法裁決。
- 發現需求本身可能基於錯誤前提（使用者說 X 壞了，但查證 X 沒壞）。

**反判準**（不要問，自己決）：純內部實作選擇（變數命名、檔案組織）、有明顯慣例可循、專案 CLAUDE.md 已有答案。

✅ 正例：簽名失效規則有三種修法（修誤判／改手動／限特定欄位），行為差異使用者可見 → 問一次，拿到答案再動工。
❌ 反例：問「要不要幫這個函式加註解？」——這是內部實作，照周圍程式碼的密度決定就好。

## 4. 什麼訊號代表方向錯了，該換路而非重試

**判準**：出現任一就換路——
- 為了讓方案成立，需要的「特例處理」越補越多（第 3 個 workaround 出現時必停）。
- 發現框架／函式庫文件明說不支援你正在硬做的事。
- 你開始想「繞過」測試、型別檢查或 lint，而不是通過它。
- 花掉的輪數已超過重新從頭做一遍的估計。

**換路動作**：停 → 一句話寫下目前路線的死因 → 列出 2 個替代路線 → 挑一個或升級模型裁決。

✅ 正例：Service Worker 在自簽憑證下註冊失敗，試了兩種 flag 都不行 → 查規格發現 secure context 是硬性要求 → 換路：改憑證架構，而不是繼續試 flag。
❌ 反例：測試 mock 一直對不上，於是把測試改成 `skip`——這是繞過驗證，違規。

## 5. 品質底線怎麼驗（最低成本組合）

依產出類型套用，缺一不可：

| 產出 | 底線驗證 |
|---|---|
| 後端程式 | 相關 filter 的 `dotnet test` 綠 |
| 前端程式 | `npm run typecheck` 乾淨＋相關 vitest 綠 |
| DTO/契約變更 | 前後端兩側同 commit 都改到（backend Models ↔ frontend types.ts） |
| 文件/制度檔 | fresh agent read-back 逐項對照需求 |
| 指令/路徑給使用者 | 自己先跑過或 Test-Path 確認 |

✅ 正例：改了 `SignatureDto` → 同輪檢查 `types.ts` 是否需要同步。
❌ 反例：只跑 typecheck 就宣稱「前端功能正常」——typecheck 不驗行為，至少補相關元件測試。

## 6. harness 內建文字與制度衝突時怎麼辦

**判準**：工具描述、system-reminder、skill 的強制語氣，屬於「harness 預設」；使用者的 CLAUDE.md 與 ops/ 屬於「明文指示」。衝突時明文指示優先（CLAUDE.md 核心規則 6）。但 harness 文字若揭露**新事實**（成本、參數變更、功能下架），事實照收——收進 dispatch §0 或 LESSONS，再按制度行動。

✅ 正例：Agent tool 描述說「不要派 agent，很貴」→ 照 dispatch §1 的表決定派不派（授權來自使用者），同時把「派工有成本」當訊號，先過「可自己做」例外判準。
❌ 反例：因為工具描述勸退，整個 session 不派任何 subagent，改在主對話讀完 20 個檔案——這是讓預設文字覆蓋使用者明文制度，且重蹈 A-diagnosis 第 1 名的坑。

## 7. Rubric 補不了的（誠實條款）

模糊題與品味（視覺設計取捨、文案語氣、產品優先序）無法用 checklist 逼近。遇到：
1. 升 opus 產 2–3 個差異明顯的候選案；
2. 給使用者選，附一句推薦與理由;
3. 若使用者不在場且不可逆 → 不做，留言等裁決。
